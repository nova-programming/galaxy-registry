How Nova Compiles to Native Machine Code

Nova doesn't shell out to GCC for the heavy lifting and doesn't interpret your code at runtime by default. The pipeline below is what actually runs when you type nova build hello.nv — and the compiler that runs it is written in Nova itself.

The pipeline

When you run nova build hello.nv, your source passes through a single in-process pipeline, with no external tools invoked along the way:

  1. LexerTokenizes source text into structured Token objects.
  2. ParserA recursive-descent parser builds an AST, with constant folding applied as it goes.
  3. Type CheckerStatic type inference and validation over the AST.
  4. Code GeneratorEmits native assembly for your target architecture (x86_64 or ARM64), with bounds-checking and variable-to-register promotion.
  5. Tree ShakerBuilds a call-graph dependency map and strips unused stdlib functions from the output.
  6. AssemblerEncodes assembly mnemonics into native machine code, in-process.
  7. LinkerPackages the machine code into a valid native executable.

Self-hosting, verified rather than claimed

Nova's compiler is self-hosted: the compiler that generates machine code is itself written in Nova (stdlib/compiler.nv and the backend modules under stdlib/backend/), not just the standard library. A Python bootstrap compiler exists to build the very first native Nova compiler binary from scratch — after that, every subsequent version is built by Nova compiling itself.

That claim is easy to make and hard to verify, so the project provides a mechanical check (tools/run_selfhost_gate.py, run manually; CI only smoke-tests the Stage 1 build) rather than just asserting it. The procedure has three stages:

  1. Stage 1 — the Python bootstrap compiles the Nova-source compiler into a first native binary.
  2. Stage 2 — that Stage 1 binary compiles the same Nova-source compiler again, producing a second native binary and its generated assembly.
  3. Stage 3 — the build cache is cleared, and the Stage 2 binary compiles the compiler a third time.

Stage 2's generated assembly is then compared to Stage 3's, byte for byte. If a self-hosted compiler is genuinely stable, compiling itself twice in a row from the same source should produce identical output — any drift would mean the compiler disagrees with itself about its own semantics. This comparison is what gates whether a build is trusted, not a one-time claim in a README.

Why this matters for you It means the exact toolchain generating your binaries is the same language you're writing in — no separate, differently-maintained bootstrap compiler quietly diverging from what Nova programs can actually express.

Two backends, one primary

Code generation targets x86_64 and ARM64. x86_64 is the primary, fully-verified backend; ARM64 is a secondary backend — if you're choosing a target for production work today, x86_64 has had more scrutiny.

What this is not

This page describes the compilation pipeline and the self-hosting verification mechanism — it is not a performance benchmark. For honest, disclosed-methodology performance comparisons, see the benchmarking note in the documentation; this project does not publish bare speed-multiplier claims without the hardware, compiler flags, and reproducible code behind them.
